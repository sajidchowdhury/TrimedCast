    22→## 1. Role Definitions
    23→
    24→The TrimedCast platform defines **five roles** within each tenant. All roles are tenant-scoped — a user's role applies only within their own tenant and grants zero access to any other tenant's data.
    25→
    26→### 1.1 Warehouse Manager (Admin role within tenant)
    27→
    28→| Aspect | Details |
    29→|--------|---------|
    30→| **Role Code** | `warehouse_manager` |
    31→| **Hierarchy Level** | 1 (highest within tenant) |
    32→| **Description** | Operational administrator with full control over products, inventory, suppliers, purchase orders, forecast configuration, and user management within their tenant. |
    33→
    34→**Capabilities:**
    35→
    36→- Full CRUD on: `Products`, `Inventory`, `Suppliers`, `Purchase Orders`, `Forecast Settings`, `Users` (within tenant)
    37→- Can approve/reject forecasts and S&OP stages
    38→- Can view: All data including unit costs, margins, supplier contracts
    39→- Can manage: Other users' roles within tenant (except elevating to `warehouse_manager` without SaaS admin approval)
    40→- Can export: All data for their tenant
    41→- Can override: Calculated values (safety stock, reorder point, EOQ) with mandatory governance note
    42→
    43→**Restrictions:**
    44→
    45→- Cannot: Modify own role
    46→- Cannot: Delete the tenant itself
    47→- Cannot: Access any other tenant's data
    48→- Cannot: Bypass the S&OP workflow (must follow stage gates)
    49→
    50→---
    51→
    52→### 1.2 Sales Manager
    53→
    54→| Aspect | Details |
    55→|--------|---------|
    56→| **Role Code** | `sales_manager` |
    57→| **Hierarchy Level** | 2 |
    58→| **Description** | Manages sales orders and has read-only visibility into product availability, inventory stock levels, and purchase order status for coordination purposes. Financial data is deliberately hidden. |
    59→
    60→**Capabilities:**
    61→
    62→- CRUD on: `Sales Orders` — can create, read, update, and delete own orders; read all orders within tenant
    63→- Read-only on:
    64→  - `Products` — **excluding** `unit_cost_bdt`, `margin_bdt`, `margin_pct`, supplier pricing fields
    65→  - `Inventory` — stock quantity levels only, not unit costs or values
    66→  - `Suppliers` — name and lead time only, not contract terms or pricing
    67→  - `Purchase Orders` — status tracking only (expected date, received qty), not cost data
    68→- Can view: Forecast results (read-only) for demand planning coordination
    69→
    70→**Restrictions:**
    71→
    72→- Cannot: View `unit_cost_bdt`, `margin_bdt`, `margin_pct`, `supplier_pricing`, `forecast_settings`
    73→- Cannot: Modify purchase orders, inventory levels, or product master data
    74→- Cannot: Approve forecasts or advance S&OP stages
    75→- Cannot: Access audit log
    76→- Cannot: Export financial data
    77→
    78→---
    79→
    80→### 1.3 Marketing Manager
    81→
    82→| Aspect | Details |
    83→|--------|---------|
    84→| **Role Code** | `marketing_manager` |
    85→| **Hierarchy Level** | 3 |
    86→| **Description** | Drives demand-side adjustments through promotional events and promo index tuning. Has visibility into forecasts and sales data for demand insight, but no access to cost or supply-chain operational data. |
    87→
    88→**Capabilities:**
    89→
    90→- CRUD on: `Promo Events`, `Promo Index` adjustments
    91→- Read-only on:
    92→  - `Products` — product names, categories, selling prices (for promo planning)
    93→  - `Forecasts` — can view but not approve or modify algorithm parameters
    94→  - `Sales Data` — aggregated demand insights, not per-unit cost breakdowns
    95→- Can adjust:
    96→  - Promo Index slider (affects the β₂ coefficient in the demand model)
    97→  - Campaign dates and promo event parameters
    98→  - Seasonal override factors for marketing-driven demand shifts
    99→
   100→**Restrictions:**
   101→
   102→- Cannot: View `unit_cost_bdt`, `margin_bdt`, `margin_pct`, `supplier_pricing`
   103→- Cannot: Modify purchase orders, inventory, or product master data
   104→- Cannot: Approve forecasts or advance S&OP stages
   105→- Cannot: Access `forecast_settings` (algorithm parameters)
   106→- Cannot: Access audit log
   107→

   109→
   110→### 1.4 Finance (Read-Only Analyst)
   111→
   112→| Aspect | Details |
   113→|--------|---------|
   114→| **Role Code** | `finance` |
   115→| **Hierarchy Level** | 4 |
   116→| **Description** | Read-only access to all financial data, forecast accuracy metrics, and the audit log. Designed for analysts who need to monitor cost-to-serve, margin performance, and forecast accuracy without any modification capability. |
   117→
   118→**Capabilities:**
   119→
   120→- Read-only access to:
   121→  - Financial data: `unit_cost_bdt`, `margin_bdt`, `margin_pct`, EOQ costs, order values, purchase order totals
   122→  - Forecast accuracy: MAPE, WMAPE, bias metrics, PvA (Plan vs Actual) analysis
   123→  - Audit log: Full read access for governance and compliance review
   124→- Special view: **Financial Coherence Dashboard**
   125→  - Cost-to-serve metrics per product category
   126→  - Cash flow projections (based on purchase order commitments and sales order pipeline)
   127→  - Margin trend analysis with seasonal decomposition
   128→  - Inventory carrying cost calculations
   129→  - EOQ vs actual order quantity variance analysis
   130→
   131→**Restrictions:**
   132→
   133→- Cannot: Modify **any** data — strictly read-only across all resources
   134→- Cannot: Approve anything (forecasts, S&OP stages, purchase orders)
   135→- Cannot: View supplier contract details (contract terms, payment terms, exclusivity clauses)
   136→- Cannot: Create, update, or delete any record
   137→- Cannot: Export data (prevents bulk financial data extraction)
   138→
   139→---
   140→
   141→### 1.5 Executive (Leadership)
   142→
   143→| Aspect | Details |
   144→|--------|---------|
   145→| **Role Code** | `executive` |
   146→| **Hierarchy Level** | 0 (strategic oversight, parallel to warehouse_manager) |
   147→| **Description** | Strategic leadership role with visibility into all data (matching warehouse_manager) plus the ability to approve S&OP stages and advance the planning cycle. Cannot perform day-to-day CRUD operations — this is a governance and approval role. |
   148→
   149→**Capabilities:**
   150→
   151→- Can: Approve S&OP stages, view all data (same visibility as `warehouse_manager`)
   152→- Can: Advance S&OP cycle to the next stage
   153→- Can: Approve or reject forecasts (overrides Sales/Marketing recommendations)
   154→- Can: Override calculated values with governance note
   155→- Special view: **Executive Dashboard**
   156→  - High-level KPIs: Total revenue, total margin, forecast accuracy, fill rate
   157→  - PvA analysis: Plan vs Actual comparison across categories
   158→  - S&OP stage progress with approval status
   159→  - Inventory health summary (stock-out risk, excess inventory)
   160→  - Cash flow summary
   161→
   162→**Restrictions:**
   163→
   164→- Cannot: CRUD on `Products`, `Inventory`, `Sales Orders`, `Purchase Orders` (strategic role, not operational)
   165→- Cannot: Modify forecast algorithm parameters
   166→- Cannot: Delete users or modify user roles
   167→- **Exception**: Can approve forecasts and advance S&OP stages (this is their primary operational function)

   314→## 3. Laravel Implementation
   315→
   316→### 3.1 Role and Permission Setup
   317→
   318→#### Role Enum
   319→
   320→```php
   321→<?php
   322→
   323→namespace App\Enums;
   324→
   325→enum Role: string
   326→{
   327→    case WAREHOUSE_MANAGER = 'warehouse_manager';
   328→    case SALES_MANAGER = 'sales_manager';
   329→    case MARKETING_MANAGER = 'marketing_manager';
   330→    case FINANCE = 'finance';
   331→    case EXECUTIVE = 'executive';
   332→
   333→    /**
   334→     * Get the hierarchy level for the role.
   335→     * Lower number = higher authority within tenant.
   336→     */
   337→    public function hierarchyLevel(): int
   338→    {
   339→        return match ($this) {
   340→            self::WAREHOUSE_MANAGER => 1,
   341→            self::SALES_MANAGER => 2,
   342→            self::MARKETING_MANAGER => 3,
   343→            self::FINANCE => 4,
   344→            self::EXECUTIVE => 0, // Strategic oversight, parallel to warehouse_manager
   345→        };
   346→    }
   347→
   348→    /**
   349→     * Roles that can view financial data (unit costs, margins, etc.)
   350→     */
   351→    public function canViewFinancials(): bool
   352→    {
   353→        return in_array($this, [
   354→            self::WAREHOUSE_MANAGER,
   355→            self::FINANCE,
   356→            self::EXECUTIVE,
   357→        ]);
   358→    }
   359→
   360→    /**
   361→     * Roles that can view supplier contract details.
   362→     */
   363→    public function canViewSupplierContracts(): bool
   364→    {
   365→        return in_array($this, [
   366→            self::WAREHOUSE_MANAGER,
   367→            self::EXECUTIVE,
   368→        ]);
   369→    }
   370→
   371→    /**
   372→     * Roles that can approve forecasts and S&OP stages.
   373→     */
   374→    public function canApproveForecasts(): bool
   375→    {
   376→        return in_array($this, [
   377→            self::WAREHOUSE_MANAGER,
   378→            self::EXECUTIVE,
   379→        ]);
   380→    }
   381→
   382→    /**
   383→     * Roles that can perform CRUD on operational data.
   384→     */
   385→    public function isOperational(): bool
   386→    {
   387→        return in_array($this, [
   388→            self::WAREHOUSE_MANAGER,
   389→            self::SALES_MANAGER,
   390→            self::MARKETING_MANAGER,
   391→        ]);
   392→    }
   393→
   394→    /**
   395→     * Roles that are strictly read-only.
   396→     */
   397→    public function isReadOnly(): bool
   398→    {
   399→        return $this === self::FINANCE;
   400→    }
   401→
   402→    /**
   403→     * Get all sensitive fields this role cannot see.
   404→     */
   405→    public function restrictedFields(): array
   406→    {
   407→        return match ($this) {
   408→            self::WAREHOUSE_MANAGER => [],
   409→            self::EXECUTIVE => [],
   410→            self::SALES_MANAGER => [
   411→                'unit_cost_bdt',
   412→                'margin_bdt',
   413→                'margin_pct',
   414→                'supplier_unit_price',
   415→                'supplier_contract_terms',
   416→                'supplier_payment_terms',
   417→                'eoq_total_cost',
   418→                'po_total_value_bdt',
   419→                'inventory_value_bdt',
   420→            ],
   421→            self::MARKETING_MANAGER => [
   422→                'unit_cost_bdt',
   423→                'margin_bdt',
   424→                'margin_pct',
   425→                'supplier_unit_price',
   426→                'supplier_contract_terms',
   427→                'supplier_payment_terms',
   428→                'eoq_total_cost',
   429→                'po_total_value_bdt',
   430→                'inventory_value_bdt',
   431→            ],
   432→            self::FINANCE => [
   433→                'supplier_contract_terms',
   434→                'supplier_payment_terms',
   435→            ],
   436→        };
   437→    }
   438→}

   864→#### Middleware: CheckRole
   865→
   866→```php
   867→<?php
   868→
   869→namespace App\Http\Middleware;
   870→
   871→use App\Enums\Role;
   872→use Closure;
   873→use Illuminate\Http\Request;
   874→use Symfony\Component\HttpFoundation\Response;
   875→
   876→class CheckRole
   877→{
   878→    /**
   879→     * Handle an incoming request.
   880→     * Usage: ->middleware('role:warehouse_manager,executive')
   881→     */
   882→    public function handle(Request $request, Closure $next, string ...$roles): Response
   883→    {
   884→        $user = $request->user();
   885→
   886→        if (! $user) {
   887→            return response()->json([
   888→                'message' => 'Unauthenticated.',
   889→            ], 401);
   890→        }
   891→
   892→        $roleEnums = array_map(
   893→            fn (string $role) => Role::from($role),
   894→            $roles
   895→        );
   896→
   897→        if (! $user->hasAnyRole(...$roleEnums)) {
   898→            // Log unauthorized access attempt for security audit
   899→            AuditLogService::logSecurityEvent(
   900→                event: 'role_access_denied',
   901→                details: [
   902→                    'required_roles' => $roles,
   903→                    'user_role' => $user->role->value,
   904→                    'route' => $request->route()?->getName(),
   905→                ],
   906→            );
   907→
   908→            return response()->json([
   909→                'message' => 'Insufficient role privileges.',
   910→            ], 403);
   911→        }
   912→
   913→        return $next($request);
   914→    }
   915→}

  1453→### 3.3 Scope-Level Security
  1454→
  1455→#### TenantScope — Global Scope for Multi-Tenancy
  1456→
  1457→```php
  1458→<?php
  1459→
  1460→namespace App\Scopes;
  1461→
  1462→use App\Models\User;
  1463→use Illuminate\Database\Eloquent\Builder;
  1464→use Illuminate\Database\Eloquent\Model;
  1465→use Illuminate\Database\Eloquent\Scope;
  1466→
  1467→class TenantScope implements Scope
  1468→{
  1469→    /**
  1470→     * Apply the tenant scope to the query.
  1471→     * Automatically adds WHERE tenant_id = current_user's tenant_id.
  1472→     */
  1473→    public function apply(Builder $builder, Model $model): void
  1474→    {
  1475→        if ($user = auth()->user()) {
  1476→            $builder->where($model->getTable() . '.tenant_id', $user->tenant_id);
  1477→        }
  1478→    }
  1479→
  1480→    /**
  1481→     * Extend the builder with a method to bypass tenant scope
  1482→     * for SaaS admin operations only.
  1483→     */
  1484→    public function extend(Builder $builder): void
  1485→    {
  1486→        $builder->macro('withoutTenantScope', function (Builder $builder) {
  1487→            return $builder->withoutGlobalScope(static::class);
  1488→        });
  1489→    }
  1490→}
  1491→```

  1560→#### SetTenantId Middleware
  1561→
  1562→```php
  1563→<?php
  1564→
  1565→namespace App\Http\Middleware;
  1566→
  1567→use Closure;
  1568→use Illuminate\Http\Request;
  1569→use Symfony\Component\HttpFoundation\Response;
  1570→
  1571→class SetTenantId
  1572→{
  1573→    /**
  1574→     * Resolve the tenant from the authenticated user and set it
  1575→     * on the request and in the PostgreSQL session variable for RLS.
  1576→     */
  1577→    public function handle(Request $request, Closure $next): Response
  1578→    {
  1579→        $user = $request->user();
  1580→
  1581→        if (! $user) {
  1582→            return $next($request);
  1583→        }
  1584→
  1585→        // Verify user's tenant is active
  1586→        if (! $user->tenant?->is_active) {
  1587→            auth()->logout();
  1588→
  1589→            return response()->json([
  1590→                'message' => 'Your organization account is inactive. Contact support.',
  1591→            ], 403);
  1592→        }
  1593→
  1594→        // Set tenant ID on the request for easy access
  1595→        $request->attributes->set('tenant_id', $user->tenant_id);
  1596→
  1597→        // Set PostgreSQL session variable for Row-Level Security
  1598→        // This is the defense-in-depth approach — even if Eloquent scope fails,
  1599→        // the database RLS policy will enforce tenant isolation.
  1600→        try {
  1601→            \DB::statement(
  1602→                "SET LOCAL app.tenant_id = ?",
  1603→                [$user->tenant_id]
  1604→            );
  1605→        } catch (\Exception $e) {
  1606→            \Log::error('Failed to set tenant session variable', [
  1607→                'user_id' => $user->id,
  1608→                'tenant_id' => $user->tenant_id,
  1609→                'error' => $e->getMessage(),
  1610→            ]);
  1611→        }
  1612→
  1613→        return $next($request);
  1614→    }
  1615→}

  1689→## 4. API Security
  1690→
  1691→### 4.1 Authentication
  1692→
  1693→TrimedCast supports **two authentication strategies** depending on the client type:
  1694→
  1695→| Client Type | Mechanism | Token Type | Expiration | CSRF |
  1696→|-------------|-----------|------------|------------|------|
  1697→| SPA (Vue.js/React) | Laravel Sanctum | Cookie-based (session) | 24 hours | ✅ Yes |
  1698→| Mobile App | Laravel Sanctum | Bearer token | 30 days | N/A |
  1699→| 3rd Party Integration | Laravel Passport | OAuth2 access token | Configurable (default 24h) | N/A |
  1700→| Service-to-Service | Static API Key + HMAC | Custom header | No expiry (key rotation) | N/A |
  1701→
  1702→#### Sanctum Configuration (SPA)
  1703→
  1704→```php

  1805→#### HMAC-SHA256 Request Signing
  1806→
  1807→```php
  1808→<?php
  1809→
  1810→namespace App\Services\Security;
  1811→
  1812→use Illuminate\Http\Request;
  1813→
  1814→class HmacSignatureService
  1815→{
  1816→    /**
  1817→     * Generate HMAC-SHA256 signature for an outgoing request.
  1818→     * Used when TrimedCast calls the Python Forecast Service.
  1819→     */
  1820→    public static function signRequest(
  1821→        string $method,
  1822→        string $url,
  1823→        string $body,
  1824→        string $hmacSecret,
  1825→    ): string {
  1826→        $timestamp = now()->timestamp;
  1827→        $nonce = bin2hex(random_bytes(16));
  1828→
  1829→        // Construct the signature payload: METHOD + URL + TIMESTAMP + NONCE + SHA256(BODY)
  1830→        $bodyHash = hash('sha256', $body);
  1831→        $payload = implode("\n", [
  1832→            strtoupper($method),
  1833→            $url,
  1834→            $timestamp,
  1835→            $nonce,
  1836→            $bodyHash,
  1837→        ]);
  1838→
  1839→        $signature = hash_hmac('sha256', $payload, $hmacSecret);
  1840→
  1841→        return base64_encode(implode(':', [
  1842→            $timestamp,
  1843→            $nonce,
  1844→            $signature,
  1845→        ]));
  1846→    }
  1847→
  1848→    /**
  1849→     * Verify HMAC-SHA256 signature on an incoming request.
  1850→     * Used when the Python Forecast Service calls back to TrimedCast.
  1851→     */
  1852→    public static function verifySignature(
  1853→        Request $request,
  1854→        string $hmacSecret,
  1855→    ): bool {
  1856→        $signatureHeader = $request->header('X-Signature');
  1857→        $parts = explode(':', base64_decode($signatureHeader));
  1858→
  1859→        if (count($parts) !== 3) {
  1860→            return false;
  1861→        }
  1862→
  1863→        [$timestamp, $nonce, $signature] = $parts;
  1864→
  1865→        // Reject requests older than 5 minutes (replay protection)
  1866→        if (abs(now()->timestamp - (int) $timestamp) > 300) {
  1867→            return false;
  1868→        }
  1869→
  1870→        // Reject replayed nonces (check Redis cache)
  1871→        $nonceKey = "hmac_nonce:{$nonce}";
  1872→        if (\Cache::has($nonceKey)) {
  1873→            return false;
  1874→        }
  1875→        \Cache::put($nonceKey, true, 300); // Store for 5 minutes
  1876→
  1877→        // Reconstruct expected signature
  1878→        $bodyHash = hash('sha256', $request->getContent());
  1879→        $payload = implode("\n", [
  1880→            strtoupper($request->method()),
  1881→            $request->fullUrl(),
  1882→            $timestamp,
  1883→            $nonce,
  1884→            $bodyHash,
  1885→        ]);
  1886→
  1887→        $expectedSignature = hash_hmac('sha256', $payload, $hmacSecret);
  1888→
  1889→        return hash_equals($expectedSignature, $signature);
  1890→    }
  1891→}
  1892→```

  1894→#### Key Rotation Support
  1895→
  1896→```php
  1897→<?php
  1898→
  1899→namespace App\Services\Security;
  1900→
  1901→use App\Models\ServiceApiKey;
  1902→use Illuminate\Support\Facades\Crypt;
  1903→
  1904→class ApiKeyRotationService
  1905→{
  1906→    /**
  1907→     * Rotate an API key with a 7-day overlap period.
  1908→     * Both old and new keys remain active during overlap.
  1909→     */
  1910→    public function rotateKey(ServiceApiKey $oldKey, string $serviceName): ServiceApiKey
  1911→    {
  1912→        // Generate new key
  1913→        $newKeyValue = 'tmc_' . bin2hex(random_bytes(32));
  1914→        $newHmacSecret = bin2hex(random_bytes(32));
  1915→
  1916→        // Create new API key record
  1917→        $newKey = ServiceApiKey::create([
  1918→            'tenant_id' => $oldKey->tenant_id,
  1919→            'service_name' => $serviceName,
  1920→            'key_prefix' => substr($newKeyValue, 0, 8),
  1921→            'key_hash' => bcrypt($newKeyValue),
  1922→            'hmac_secret' => Crypt::encryptString($newHmacSecret),
  1923→            'is_active' => true,
  1924→            'expires_at' => null, // No expiry — manual rotation only
  1925→            'allowed_ips' => $oldKey->allowed_ips,
  1926→            'rate_limit' => $oldKey->rate_limit,
  1927→        ]);
  1928→
  1929→        // Schedule old key deactivation in 7 days
  1930→        $oldKey->update([
  1931→            'expires_at' => now()->addDays(7),
  1932→        ]);
  1933→
  1934→        // Dispatch job to deactivate old key after 7 days
  1935→        \App\Jobs\DeactivateApiKeyJob::dispatch($oldKey)
  1936→            ->delay(now()->addDays(7));
  1937→
  1938→        return $newKey;
  1939→        // Return the new key value to the caller ONCE
  1940→        // It is never stored in plaintext in the database
  1941→    }
  1942→}
